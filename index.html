Three Kubernetes clusters, run from Git

This repository builds a dev staging prod set of on-premises Kubernetes clusters and everything that runs on them. After a one-time setup, every change is a pull request. This page is written for people new to the project: read it top to bottom once, then use the menu.

Ansible

Builds each cluster with kubeadm: HA control plane behind a kube-vip address, Calico networking. Runs from GitHub Actions on a runner inside the LAN.

Argo CD

One per cluster. Reconciles MetalLB, F5 NGINX Ingress, Kyverno, itself and the demo app from gitops/clusters/<env>.

Promotion

A button copies the release from dev to staging, or staging to prod, as a pull request that a second person approves.

Guard rails

Separate subnets, pre-flight checks, CI cross-checks and a cluster policy make it hard to touch the wrong environment.

The demo app is nginx showing K8s Demo, the environment, the release version and the pod that answered: http://dev.k8sdemo.vn, http://staging.k8sdemo.vn, http://k8sdemo.vn.

Read this first: the ideas in two minutes

IaC / GitOpsEvery server setting and every Kubernetes object is a file in this repository. You change the system by merging a pull request, never by typing commands on a server.

What ansible/site.yml does, in order

  1. Pre-flight (every node): the inventory folder, the node's subnet and the marker file /etc/k8s-demo/env must all name the same environment, otherwise the whole run stops before anything changes.
  2. Common (every node): proxy for apt and containerd, hostname, /etc/hosts, swap off, kernel modules and sysctl, containerd with the systemd cgroup driver, kubelet/kubeadm/kubectl from pkgs.k8s.io (held at the pinned minor version).
  3. Control plane: on a new cluster, checks that the VIP and the MetalLB pool are unused; starts kube-vip; kubeadm init on the first control plane; installs Calico; joins the other control planes. A node whose earlier join failed halfway is reset and joined again.
  4. Workers: join the cluster.
  5. Hand-over to Argo CD (first control plane): writes kube-system/cluster-identity, installs Argo CD if it is missing, sets the admin password from the GitHub secret, and applies the root Application. From here on Argo CD owns everything inside the cluster.

Running it again is safe: finished steps are skipped.

Automation switch

Every workflow (validate, ansible, drift, promote) is off until the repository variable AUTOMATION_ENABLED is true. Pushing the repository runs nothing, and skipped jobs count as passed checks.

gh variable set AUTOMATION_ENABLED --body true --repo haison8x/k8s-demo   # on
gh variable delete AUTOMATION_ENABLED --repo haison8x/k8s-demo           # off

Or use Settings → Secrets and variables → Actions → Variables. Turning it off also stops the nightly drift check; it does not stop Argo CD, which keeps syncing the clusters from main.

Before you start

Access you need

  • Admin rights on the GitHub repository haison8x/k8s-demo (for github-setup.sh and the GitHub App), or write access to contribute.
  • SSH access as user haison (passwordless sudo) to the servers of the environment you work on.
  • A workstation in the LAN: Windows with WSL2 (Ubuntu), or Linux.

Tools on your workstation

sudo apt-get install -y git curl openssl python3   # basic tools (once)
# GitHub CLI: https://cli.github.com  then:

git clone https://github.com/haison8x/k8s-demo.git ~/k8s-demo && cd ~/k8s-demo

One-time setup

Do the steps in this order. Steps 1–5 change nothing on a server; step 7 builds the clusters.
  1. SSH keys. One key pair per environment plus one for the runner. Replace the placeholder keys: 
    mkdir -p ~/.ssh/k8s-demo && chmod 700 ~/.ssh/k8s-demo
for k in dev staging prod ops; do ssh-keygen -t ed25519 -N "" -C "k8s-demo-$k" -f ~/.ssh/k8s-demo/$k; done
    The private keys never go into Git; github-setup.sh copies them into GitHub environment secrets.
  2. Servers and network. Ubuntu 24.04 everywhere, addresses as in the table, user haison with passwordless sudo. Add ~/.ssh/k8s-demo/<env>.pub to ~haison/.ssh/authorized_keys on that environment's servers (ops.pub on ops1), for example ssh-copy-id -i ~/.ssh/k8s-demo/dev.pub haison@172.20.2.5. Firewall: dev and staging cannot reach prod; ops1 reaches every subnet on SSH; the presenter laptop reaches each ingress IP on port 80 and the prod VIP on 6443. Make sure nothing uses the VIP (.100) or the MetalLB range (.200–.229) of each subnet, and that the nodes of one environment share one layer-2 network (kube-vip and MetalLB answer ARP).
  3. GitHub App k8s-demo-promoter. It opens the promotion pull requests, because pull requests opened by the default workflow token do not start CI.
    1. GitHub → your avatar → Settings → Developer settings → GitHub Apps → New GitHub App.
    2. Name k8s-demo-promoter, homepage https://github.com/haison8x/k8s-demo, untick Webhook → Active.
    3. Repository permissions: Contents Read and write, Pull requests Read and write (Metadata read-only is added automatically).
    4. "Where can this GitHub App be installed?": Only on this account. Create it.
    5. Note the Client ID; Generate a private key (a .pem file is downloaded).
    6. Install App → only the repository k8s-demo.
  4. GitHub settings. Preview first, then apply, as a repository admin: 
    gh auth login
bash scripts/github-setup.sh --dry-run
bash scripts/github-setup.sh --promoter-client-id <CLIENT_ID> --promoter-key-file <key.pem>
    It sets the read-only workflow token and fork approval, creates the main-protection ruleset, invites haison9x with write access (accept the invitation), creates the environments dev, staging, prod and their -drift twins (prod needs an approval), stores the secrets and enables GitHub Pages. It prints each Argo CD admin password once: store them in your password manager. It is safe to run again; existing passwords are kept. Delete the downloaded .pem afterwards.
  5. Runner. Register ops1 as the self-hosted runner: 
    ansible-playbook -i ansible/inventories/ops/hosts.yml ansible/ops.yml --private-key ~/.ssh/k8s-demo/ops \
  -e runner_registration_token=$(gh api -X POST repos/haison8x/k8s-demo/actions/runners/registration-token --jq .token)
    ops1 then appears under Settings → Actions → Runners with the label k8s-demo-ops.
  6. Turn automation on: gh variable set AUTOMATION_ENABLED --body true --repo haison8x/k8s-demo.
  7. Build the clusters. Actions → ansible → Run workflow: env dev, playbook site. Check dev, then staging, then prod; the prod run waits for an approval. The first run checks that the VIP and the MetalLB pool are unused before kubeadm init. Expect roughly 15–30 minutes for a first build.
  8. Name resolution on the presenter laptop (C:\Windows\System32\drivers\etc\hosts, edited as administrator) or in LAN DNS: 
    172.20.2.200 dev.k8sdemo.vn argocd.dev.k8sdemo.vn
172.20.1.200 staging.k8sdemo.vn argocd.staging.k8sdemo.vn
172.20.0.200 k8sdemo.vn argocd.k8sdemo.vn
  9. kubectl (optional). Each environment gets its own file and context k8s-demo-<env>, never merged into ~/.kube/config: 
    scripts/get-kubeconfig.sh prod
export KUBECONFIG=~/.kube/k8s-demo-prod.kubeconfig
kubectl get nodes
  10. Argo CD UI: http://argocd.<env>.k8sdemo.vn (prod: http://argocd.k8sdemo.vn), user admin, password from step 4.

APP_MESSAGE in release.yaml must not contain quotes, $, ;, braces or backslashes (it is inserted into the nginx configuration). Component versions are listed in docs/VERSIONS.md.

Promotion

Each environment's overlay has two files. env.yaml holds what belongs to the environment and is never promoted. release.yaml holds what is being released — the image, APP_VERSION and APP_MESSAGE — and is copied unchanged from one environment to the next.

Edit dev release.yaml→ PR · CI green · merge→ dev updates→ promote dev-to-staging→ bot PR · code owner approves→ staging updates→ promote staging-to-prod→ prod updates

Changes to base/, gitops/platform/, roles or workflows reach every environment at once, so they always need a code owner review. Keep anything that should roll out gradually in release.yaml or in the per-environment Application files.

Guard rails against touching the wrong environment

LayerProtection
NetworkOne subnet per environment; dev and staging cannot reach prod; static addresses only.
AnsibleNo default inventory. A pre-flight check refuses to run when the inventory folder, the host subnet and the /etc/k8s-demo/env marker on the node disagree. A free-IP check runs before the first kubeadm init. Reset requires typing the environment name.
CredentialsOne SSH key per environment, stored in that GitHub environment. Prod runs need an approval. Nothing secret is printed in the public workflow logs.
VisibilityHostnames carry the environment (prod-cp1); one kubeconfig file and context per environment; a permanent Argo CD banner; the page banner shows the environment in its colour.
ClusterA Kyverno policy, identical everywhere, rejects resources labelled for another environment. It reads the environment from kube-system/cluster-identity, written by Ansible — two independent sources that must agree.
Git and CIOne pull request may change one environment. scripts/env-guard.py checks hosts, IPs, proxy settings and Application paths against each inventory. CODEOWNERS and a ruleset protect staging, prod and shared paths.

Contributing

  1. Create a branch: git switch -c <short-name>.
  2. Change one environment per pull request (shared paths are fine on their own).
  3. Run the checks locally (Docker is needed for the page smoke test): 
    bash scripts/validate.sh
    It runs yamllint, actionlint, shellcheck, Ansible syntax and lint, the pre-flight and reset tests, the Kyverno policy tests, the page smoke test, the environment guard and the repository tests.
  4. Push and open a pull request. validate must be green (when automation is on); staging, prod and shared paths need a code owner's approval.
  5. After merge, watch the change in that environment's Argo CD.

Write everything in English.

Running Ansible by hand

For debugging only; normal runs go through the ansible workflow, which adds the approval and the audit trail. From your clone:

export ARGOCD_ADMIN_PASSWORD='<the password of this environment>'   # only read on the first build

Demo runbook

  1. The three clusters. Open http://argocd.dev.k8sdemo.vn, http://argocd.staging.k8sdemo.vn and http://argocd.k8sdemo.vn: every application is Synced and Healthy; note the environment banners.
  2. The app. Open the three app URLs. Refresh prod a few times: the pod name changes between three pods on three workers.
  3. A change in dev. Edit APP_MESSAGE in gitops/apps/demo-app/overlays/dev/release.yaml, open a PR, merge after CI is green. Watch dev's Argo CD roll the pods and the page change.
  4. Promotion. Actions → promote → dev-to-staging. Show the bot's PR containing a single file, approve, merge. Repeat with staging-to-prod.
  5. Guard rails. Open a PR that edits both the dev and prod overlays: the validate check fails. On prod, try kubectl -n demo create configmap unlabelled --from-literal=x=1: the cluster denies it.
  6. Self-healing. kubectl -n demo scale deployment demo-app --replicas=1 on prod: Argo CD puts it back to three.
  7. High availability. Power off prod-cp1: kubectl get nodes still answers through 172.20.0.100. Power off a worker: its pod is rescheduled and the page keeps answering.

Troubleshooting

A workflow shows "skipped"

Automation is off: set AUTOMATION_ENABLED to true. ansible, drift and promote also only run from main.

The ansible run waits forever

The runner ops1 is offline (Settings → Actions → Runners) or the prod run is waiting for approval (the run page shows a review button).

Pre-flight fails: "environment marker … says 'x' but this run targets 'y'" or "… is outside 172.20.x.0/24"

You chose the wrong environment, or the server was reused from another one. Check the inventory; to reuse a server, run reset in its old environment first.

"IP … is already in use on the network" on the first build

Something on the network answers on the API VIP or a MetalLB address. Free it, or change the addresses in the inventory and the matching overlays (ip-pool.yaml, values-<env>.yaml) in one PR.

apt or image pulls time out

The proxy blocks a host (see What the proxy must allow). kubectl get pods -A shows ImagePullBackOff with the image name.

Argo CD cannot fetch the repository or a chart

Check the proxy settings in gitops/platform/argocd/overlays/<env>/proxy-env-*.yaml; they must match the inventory (CI checks this). Internal names such as .svc and the cluster ranges must stay in NO_PROXY.

An Application stays OutOfSync or Degraded

Open it in Argo CD; the event list names the failing object. Later waves wait for earlier ones to be Healthy.

A sync is denied by Kyverno

The resource's k8sdemo.vn/env label does not match the cluster. Check that the Application points at the right overlay.

The drift run fails

Someone changed a node by hand. The run's diff names the host and file. Re-run ansible site to restore it, or commit the change if it should stay.

http://k8sdemo.vn does not open

Check the hosts file entry, then curl -H 'Host: k8sdemo.vn' http://172.20.0.200.

Lost the Argo CD admin password

Patch argocd-secret in that cluster with a new bcrypt hash in the key admin.password (for example htpasswd -nbBC 10 "" '<new password>' | tr -d ':\n', package apache2-utils), then restart argocd-server. Also update the environment secret, although it is only read on the first build.

validate says "this change touches more than one environment"

Split it: one pull request per environment, shared files separately.

Known limitations

  • HTTP only: no TLS, no public DNS; access from the LAN through a hosts file or LAN DNS.
  • No etcd backups, monitoring or log collection.
  • Kyverno runs one admission replica: while that pod restarts, writes to the demo namespace are briefly refused.
  • Changing kube_minor or calico_version does not upgrade a running cluster; upgrades are a manual, planned operation (or reset + site).
  • Changing ARGOCD_ADMIN_PASSWORD after the first build has no effect.
  • On a host built before the environment marker existed, the first drift run reports the marker as a change.
  • The Kubernetes patch version and containerd come from the latest packages of their channels; only the minor version is pinned.
